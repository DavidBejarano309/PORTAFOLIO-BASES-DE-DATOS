    PL/SQL avanzado en Oracle Database

    Cómo funciona PL/SQL por dentro y cómo escribir código que rinda, resista la concurrencia y se pueda diagnosticar

    Autor
    David Felipe Bejarano Montes
    Versión de referencia
    Oracle Database 19c (con notas de 21c y 23ai)
    Fecha
    3 de noviembre de 2026

    Resumen

    PL/SQL es el lenguaje de programación de Oracle y se ejecuta dentro del mismo motor de la base de datos. Eso lo hace muy cómodo para trabajar con datos, pero también hace que los errores de diseño se noten más: una sentencia SQL puesta dentro de un bucle, una transacción que dura demasiado o un error que nadie ve pueden afectar a todo el sistema.

    En este trabajo reuní lo que hace falta para pasar de escribir procedimientos y triggers que simplemente funcionan a escribir código que aguante volumen, usuarios concurrentes y cambios en el esquema. Los temas son cómo se ejecuta PL/SQL, los paquetes, las colecciones, el procesamiento masivo, el SQL dinámico, las funciones llamadas desde SQL, las transacciones y los bloqueos, los triggers, el manejo de errores, la seguridad, el diagnóstico y las pruebas. En cada uno explico cómo funciona, pongo un ejemplo y comento cuándo conviene usarlo y cuándo no.

    Ideas principales

    1. Casi toda la optimización en PL/SQL consiste en cruzar menos veces entre el motor PL/SQL y el motor SQL. Para eso sirven BULK COLLECT y FORALL, y todavía mejor es resolver todo en una sola sentencia SQL.
    2. Las variables de enlace son la defensa principal contra la inyección SQL. Lo que no se puede enlazar, como los nombres de tablas, se valida con DBMS_ASSERT.
    3. La consistencia ante concurrencia no viene sola. Hay que elegir entre FOR UPDATE, SKIP LOCKED o una columna de versión, y bloquear siempre en el mismo orden para evitar interbloqueos.
    4. Un WHEN OTHERS que no relanza el error esconde problemas y deja datos a medias sin que nadie se entere.
    5. Antes de optimizar hay que medir. El perfilador jerárquico (DBMS_HPROF) separa el tiempo de PL/SQL del de SQL y muestra dónde está el cuello de botella.

    1. Arquitectura y ejecución de PL/SQL

    1.1 Dos motores y una frontera

    PL/SQL tiene su propio motor para compilar y ejecutar el código. Según la documentación de Oracle, ese motor ejecuta directamente las sentencias procedimentales (asignaciones, condicionales, bucles, llamadas a subprogramas) y le pasa las sentencias SQL al motor SQL de la base de datos [2]. Cada vez que el control pasa de un motor al otro se habla de un cambio de contexto, y cada sentencia SQL ejecutada desde PL/SQL implica uno [11].

    Un cambio de contexto aislado cuesta muy poco. El problema aparece cuando se repite miles de veces: si un bucle actualiza 10.000 filas de a una, son 10.000 cambios de contexto. Tom Kyte llamaba a esto slow-by-slow processing [11]. Es la idea que más conecta el resto del documento, porque casi todas las técnicas de rendimiento de PL/SQL se reducen a cruzar esa frontera menos veces.

    1.2 Unidades PL/SQL

    La documentación llama unidad PL/SQL a cualquiera de estas [2]:

    • un bloque anónimo;
    • una función, un procedimiento, una biblioteca (LIBRARY) o un trigger;
    • la especificación y el cuerpo de un paquete;
    • la especificación y el cuerpo de un tipo.

    La diferencia práctica entre un bloque anónimo y una unidad almacenada es que la unidad se guarda en la base de datos con CREATE [OR REPLACE] y conserva, junto con sus metadatos, los parámetros con los que se compiló. El bloque anónimo no se guarda, así que no tiene metadatos que reutilizar [2]. Por eso lo almacenado sirve para versionar, dar permisos y reutilizar desde cualquier sesión, y lo anónimo se queda para pruebas y scripts.

    1.3 Parámetros de compilación

    Cada unidad almacenada se compila con unos parámetros que quedan guardados con ella [2]:

    ParámetroQué controla
    PLSQL_CODE_TYPEINTERPRETED (valor predeterminado) o NATIVE
    PLSQL_OPTIMIZE_LEVELNivel de optimización del compilador. Con valor 1 se genera código apto para el depurador
    PLSQL_WARNINGSActiva o desactiva advertencias del compilador y define cuáles se tratan como error
    PLSQL_CCFLAGSBanderas para la compilación condicional
    PLSCOPE_SETTINGSRecolección de datos de identificadores para PL/Scope
    NLS_LENGTH_SEMANTICSSi CHAR y VARCHAR2 miden su longitud en bytes o en caracteres

    Con PLSQL_CODE_TYPE = NATIVE las unidades se compilan a código máquina y se ejecutan sin pasar por el intérprete de bytecode. Con INTERPRETED se compilan a bytecode que ejecuta el intérprete de PL/SQL [3]. Hay tres cosas que conviene tener presentes:

    • cambiar el parámetro no afecta a las unidades que ya estaban compiladas [3];
    • una unidad compilada como NATIVE sigue recompilándose como NATIVE en sus recompilaciones automáticas [3];
    • si PLSQL_OPTIMIZE_LEVEL es menor que 2, el compilador genera código interpretado aunque se pida NATIVE, y lo avisa con una advertencia [2].

    La compilación nativa ayuda más cuando el código hace mucho cálculo (bucles, aritmética, manejo de cadenas) y casi nada cuando el tiempo se va en SQL, porque ahí lo gasta el motor SQL y no el intérprete.

    Para ver esta configuración se usa la vista ALL_PLSQL_OBJECT_SETTINGS, o USER_PLSQL_OBJECT_SETTINGS si solo interesa el esquema propio [2].

    1.4 Dependencias e invalidación

    Una unidad almacenada depende de los objetos que usa (tablas, vistas, otros paquetes). Si uno de esos objetos cambia, Oracle marca como INVALID las unidades que dependen de él y las vuelve a compilar la siguiente vez que alguien las llama. En un sistema real esto trae tres consecuencias:

    • si la unidad invalidada ya no compila, deja de estar disponible hasta que se corrija;
    • recompilar con el sistema en uso puede generar esperas, porque la recompilación necesita acceso exclusivo a la unidad;
    • separar especificación y cuerpo ayuda: si solo cambia el cuerpo, las unidades que dependen de la especificación no se invalidan.

    Para tener en cuenta

    Después de cualquier cambio en el esquema conviene revisar USER_OBJECTS (estado INVALID) y USER_ERRORS antes de dar el despliegue por terminado.

    2. Diseño modular con paquetes

    2.1 Por qué usar paquetes

    Un paquete reúne tipos, constantes, excepciones, cursores y subprogramas relacionados en dos partes: la especificación, que es la interfaz pública, y el cuerpo, que es la implementación. Las ventajas que encontré son estas:

    • Encapsulación: lo que no aparece en la especificación es privado, así que quien usa el paquete no puede depender de detalles internos.
    • Menos invalidaciones: cambiar el cuerpo sin tocar la especificación no invalida a quienes la usan.
    • Sobrecarga: varios subprogramas pueden llamarse igual si tienen firmas distintas.
    • Estado: las variables del paquete duran lo que dure la sesión, lo que sirve para cachés pequeñas o contadores.
    • Carga en bloque: al llamar un subprograma se carga todo el paquete en memoria, y las llamadas siguientes ya no repiten la carga.

    La excepción e_stock_insuficiente queda vinculada al código -20101 con PRAGMA EXCEPTION_INIT. Así, quien llama al paquete puede capturarla por su nombre (WHEN pck_inventario.e_stock_insuficiente) en lugar de comparar números de error, y dentro del cuerpo se sigue usando RAISE_APPLICATION_ERROR para agregar un mensaje que explique qué pasó.

    2.2 El estado del paquete

    Las variables declaradas en la especificación o en el cuerpo, fuera de los subprogramas, conservan su valor durante la sesión. Es útil para cachés pequeñas, contadores o configuración. Pero el estado es por sesión y no global, y eso importa en dos casos:

    • Con agrupaciones de conexiones (connection pools), una misma sesión atiende a clientes distintos en momentos distintos. Si el estado asume un solo usuario por sesión, puede pasar información de un cliente a otro.
    • Al recompilar el paquete, las sesiones que tenían estado reciben ORA-04068 («existing state of packages has been discarded») en su siguiente llamada.

    Por eso lo razonable es guardar en el estado solo datos que se puedan reconstruir sin pérdida y exponerlos mediante funciones, no mediante variables públicas.

    2.3 Limitar quién puede llamar: ACCESSIBLE BY

    Desde Oracle 12.2 una unidad puede indicar con ACCESSIBLE BY qué otras unidades tienen permitido llamarla. Sirve para tener subprogramas internos fuera del paquete, por ejemplo cuando se divide un paquete grande en varios archivos, sin dejarlos disponibles para el resto de la aplicación.

    Si otro bloque intenta llamarlo, falla al compilar con PLS-00904 (privilegio insuficiente para acceder al objeto).

    3. Tipos compuestos y colecciones

    3.1 Registros y %ROWTYPE

    Un registro agrupa campos de tipos distintos bajo un solo nombre. Con %ROWTYPE el registro copia la estructura de una tabla, una vista o un cursor, y se actualiza solo cuando la tabla cambia y se recompila el código. %TYPE hace lo mismo pero para una sola columna. Los dos evitan un error muy común, que es declarar a mano un VARCHAR2(50) cuando la columna ya creció a 100.

    3.2 Los tres tipos de colección

    PL/SQL tiene tres tipos de colección y cada uno sirve para algo distinto:

    3.3 Métodos de colección

    Las colecciones traen métodos propios: COUNT, FIRST, LAST, NEXT, PRIOR, EXISTS, EXTEND, TRIM y DELETE. Hay dos errores que se repiten bastante. Uno es usar LAST o COUNT como límite de un bucle sobre una colección dispersa, porque los índices intermedios no existen. El otro es olvidar EXTEND antes de asignar a una posición nueva de una tabla anidada, lo que produce ORA-06533 (subscript beyond count).

    3.4 Expresiones calificadas y nuevas formas de iterar

    Desde 18c, las expresiones calificadas permiten construir cualquier valor PL/SQL (registros, arreglos asociativos) nombrando los elementos dentro de la misma expresión [8]. La versión 21c agregó controles de iteración ampliados, entre ellos el rango con paso [8].

    4. Procesamiento masivo: BULK COLLECT y FORALL

    4.1 El problema de procesar fila por fila

    Leer en un bucle y hacer un UPDATE por cada fila es el patrón que más problemas de rendimiento causa en PL/SQL. Cada iteración manda una sentencia al motor SQL, con su cambio de contexto [11]. Para resolverlo hay un orden de preferencia:

    1. Hacerlo con una sola sentencia SQL (un UPDATE o un MERGE con la lógica en el WHERE y el SET). Es lo más rápido y lo más simple.
    2. Si la lógica no cabe en SQL, procesar por lotes: BULK COLLECT para leer y FORALL para escribir.
    3. Solo si nada de lo anterior aplica, procesar fila por fila.

    4.2 BULK COLLECT con LIMIT

    BULK COLLECT trae muchas filas en un solo cambio de contexto y las deja en colecciones. Si no se le pone límite, una consulta grande puede agotar la memoria PGA, y por eso se recomienda usar un cursor explícito con FETCH ... BULK COLLECT INTO ... LIMIT n dentro de un bucle [11]. El artículo de Oracle dice que rara vez conviene un límite menor a 100 [11]. Además, un bucle FOR sobre un cursor ya se optimiza solo para traer 100 filas por vez cuando el nivel de optimización es 2 o mayor, y ese valor no se puede cambiar [11].

    Ojo con %NOTFOUND y LIMIT

    En el último FETCH con LIMIT pueden llegar filas y a la vez activarse %NOTFOUND. Si el EXIT WHEN cur%NOTFOUND está justo después del FETCH, esas últimas filas se pierden [11]. Lo más seguro es salir cuando colección.COUNT = 0 o mover la condición al final del bucle, después de procesar el lote.

    4.3 FORALL: escribir por lotes

    FORALL le manda al motor SQL una sola sentencia de DML (INSERT, UPDATE, DELETE o MERGE) junto con todos los valores de la colección. Aunque se escriba parecido, no es un bucle: es una instrucción única que recorre un rango de índices.

    4.4 Errores dentro de un lote: SAVE EXCEPTIONS

    Por defecto, si una fila del lote falla, FORALL se detiene y se deshacen las filas que esa sentencia ya había procesado. Con SAVE EXCEPTIONS sigue con el resto y deja el detalle de los fallos en SQL%BULK_EXCEPTIONS. Al terminar lanza ORA-24381 (errores en DML de arreglo), que hay que capturar para revisar qué filas fallaron.

    4.5 Colecciones dispersas y RETURNING

    • FORALL i IN INDICES OF colección recorre solo los índices que existen en una colección dispersa. VALUES OF permite recorrer los índices que indique otra colección.
    • SQL%BULK_ROWCOUNT(i) dice cuántas filas afectó cada ejecución individual del lote.
    • RETURNING ... BULK COLLECT INTO recupera de una sola vez los valores de las filas afectadas por un DML.

    4.6 Cuándo usar cada técnica

    SituaciónTécnicaRazón
    La lógica cabe en SQLUna sola sentencia (UPDATE, MERGE, INSERT ... SELECT)No hay cambios de contexto y el optimizador ve todo el trabajo
    Hay lógica por fila y mucho volumenBULK COLLECT ... LIMIT + FORALLSe cruza la frontera una vez por lote

    5. SQL dinámico y prevención de inyección

    5.1 Cuándo hace falta

    El SQL dinámico arma y ejecuta sentencias mientras el programa corre. Se necesita cuando el texto completo de la sentencia no se conoce al compilar, por ejemplo en consultas ad hoc, o cuando hay que ejecutar DDL desde PL/SQL, que no lo permite de forma estática [4]. Oracle ofrece dos mecanismos [4]:

    • SQL dinámico nativo, con EXECUTE IMMEDIATE y OPEN ... FOR. Es más fácil de leer y escribir y, según la documentación, más rápido, sobre todo cuando el compilador puede optimizarlo.
    • El paquete DBMS_SQL, una API para construir, ejecutar y describir sentencias. Es obligatorio cuando no se conoce al compilar el número o el tipo de las columnas o de las variables de enlace, o cuando se quiere devolver resultados de forma implícita sin un parámetro OUT REF CURSOR.

    Se puede pasar de uno a otro con DBMS_SQL.TO_REFCURSOR y DBMS_SQL.TO_CURSOR_NUMBER [4]. En la práctica se usa el nativo por defecto y DBMS_SQL solo cuando el nativo no alcanza.

    5.2 Sintaxis básica

    En las sentencias SQL dinámicas, los marcadores de posición (:id, :nuevo) se asocian con la lista USING por posición, no por nombre.

    5.3 Inyección SQL

    La inyección ocurre cuando datos que escribe el usuario se concatenan en el texto de la sentencia y terminan interpretándose como código. La documentación de Oracle trata el tema en el capítulo de SQL dinámico y propone dos defensas: variables de enlace y validación [4].

    Con variable de enlace el texto de la sentencia siempre es el mismo y el valor nunca se interpreta como SQL. Además el motor reutiliza el plan que ya analizó, lo que reduce el trabajo de análisis (parse) en el servidor.

    5.4 Lo que no se puede enlazar: DBMS_ASSERT

    Los identificadores, como nombres de tablas o columnas, no aceptan variables de enlace. Para esos casos se valida la entrada con DBMS_ASSERT, que lanza una excepción si el valor no es lo que se esperaba:

    FunciónQué haceError si falla
    ENQUOTE_LITERALEnvuelve en comillas simples y escapa las internasORA-06502 si ya tiene comillas sin escapar
    ENQUOTE_NAMEEnvuelve un identificador en comillas dobles (opcionalmente en mayúsculas)ORA-44003
    SIMPLE_SQL_NAMEVerifica que sea un nombre simple, sin calificarORA-44003
    QUALIFIED_SQL_NAMEVerifica que sea un nombre que puede ir calificado (esquema.objeto)ORA-44004
    SCHEMA_NAMEVerifica que el esquema existaORA-44001
    SQL_OBJECT_NAMEVerifica que el objeto exista y sea accesibleORA-44002

    Sobre los códigos de error

    Los códigos de la tabla salen de las excepciones documentadas de DBMS_ASSERT. Si la aplicación va a depender de ellos, conviene confirmarlos en la documentación de la versión instalada y capturar la excepción en vez de comparar el número.

    Resumen

    Los valores se enlazan. Los identificadores se validan con DBMS_ASSERT o se comparan contra una lista fija escrita en el código. No se concatena texto del usuario sin alguna de las dos protecciones.

    6. Funciones invocadas desde SQL

    Cuando una sentencia SQL llama a una función PL/SQL, hay un cambio de contexto por cada fila en la que se evalúa. Un SELECT sobre un millón de filas que llame a una función serían un millón de cruces. Oracle ofrece varios mecanismos para reducir o evitar ese costo, y en esta sección los comparo.

    6.1 DETERMINISTIC y PRAGMA UDF

    DETERMINISTIC es una promesa del programador: con los mismos argumentos la función siempre devuelve lo mismo y no depende de datos de tablas ni de la fecha. Le permite al motor reutilizar resultados dentro de una misma sentencia y es necesario para usar la función en un índice basado en funciones. Oracle no comprueba la promesa, así que si es falsa los resultados serán inconsistentes.

    PRAGMA UDF, disponible desde Oracle 12c, indica que la función se va a usar sobre todo desde SQL y deja que el compilador la genere de modo que llamarla desde una sentencia SQL cueste menos. Solo tiene sentido en funciones que de verdad se llaman desde SQL.

    6.2 La cláusula WITH FUNCTION

    Desde Oracle 12c una consulta puede declarar funciones locales en su cláusula WITH. La función existe solo mientras dura la sentencia, no se crea en el esquema y tiene menos sobrecarga que una función almacenada llamada desde SQL. Sirve para lógica auxiliar de un único informe. En algunos contextos (por ejemplo DML o PL/SQL estático) puede hacer falta el hint WITH_PLSQL, así que conviene revisar la documentación de la versión que se use.

    6.3 Caché de resultados: RESULT_CACHE

    Una función marcada con RESULT_CACHE guarda en memoria compartida los resultados para cada combinación de argumentos. Si se la vuelve a llamar con los mismos argumentos, devuelve el valor guardado sin ejecutar el cuerpo. Oracle invalida la entrada automáticamente cuando cambian los datos de las tablas de las que depende la función. En 21c el mecanismo mejoró con control de sentencias y objetos excluidos, historial de funciones y volcado a disco, y el umbral RESULT_CACHE_EXECUTION_THRESHOLD decide qué se guarda [8].

    ConvieneNo conviene
    Datos de referencia que casi no cambian (catálogos, parámetros)Tablas que se modifican todo el tiempo, porque la caché se invalida constantemente
    Funciones costosas llamadas muchas veces con los mismos argumentosFunciones que dependen de SYSDATE, del usuario o del contexto de la sesión
    Pocas combinaciones distintas de argumentosArgumentos casi únicos en cada llamada, que llenan la memoria sin reutilizarse

    6.4 Funciones de tabla en tubería (pipelined)

    Una función de tabla en tubería devuelve las filas a medida que las produce, con PIPE ROW, en lugar de armar toda la colección en memoria. Se consulta con el operador TABLE como si fuera una tabla y es útil para transformar datos o encadenar etapas sin guardar resultados intermedios.

    6.5 Macros SQL

    Una macro SQL es una función que en vez de devolver un valor devuelve un fragmento de texto SQL, que el motor incorpora a la sentencia que la llama. Como la lógica ya es SQL, no hay cambio de contexto al ejecutar. Las macros de tabla, que se usan en la cláusula FROM como una vista con parámetros, se admiten desde la actualización 19.7 [9]. Las macros SQL en general, incluidas las escalares, son una novedad de 21c [8].

    7. Transacciones y concurrencia en PL/SQL

    7.1 Atomicidad en tres niveles

    Oracle garantiza atomicidad por sentencia: si una sentencia falla, se deshace completa y la transacción sigue. Encima de eso PL/SQL ofrece:

    • COMMIT y ROLLBACK para toda la transacción;
    • SAVEPOINT y ROLLBACK TO para deshacer solo hasta un punto marcado;
    • la transacción autónoma, que corre aparte de la transacción que la llama.

    Un patrón común en los procedimientos de negocio es marcar un punto al inicio y volver a él si algo falla, dejando que quien llamó decida qué hacer con la transacción exterior:

    7.2 Transacciones autónomas

    PRAGMA AUTONOMOUS_TRANSACTION hace que un subprograma corra en una transacción propia. Puede confirmar o revertir sin afectar a la transacción que lo llamó, y al revés. El uso más legítimo es el registro de errores, que tiene que quedar guardado aunque la transacción principal se revierta.

    Precauciones

    • La transacción autónoma no ve los cambios sin confirmar de la transacción principal.
    • Si termina con cambios pendientes, Oracle lanza ORA-06519, así que debe hacer COMMIT o ROLLBACK antes de retornar.
    • Usarla para saltarse un bloqueo o para forzar un orden de confirmación es señal de mal diseño. Conviene dejarla para auditoría y registro.

    7.3 Bloqueo explícito de filas

    La lectura consistente de Oracle no bloquea: dos sesiones pueden leer el mismo saldo y escribir cada una su resultado, y así se pierde una actualización. Esto fue justo lo que vimos en el taller de Banco Andino, donde dos retiros sobre la misma cuenta dejaron 800.000 en lugar de 500.000. Cuando una decisión depende de un valor que otra sesión puede estar cambiando, se bloquea la fila con SELECT ... FOR UPDATE, como hace sp_registrar_salida en el Código 2.1. Frente a una fila ya bloqueada hay cuatro comportamientos posibles:

    CláusulaComportamientoCaso de uso
    FOR UPDATEEspera indefinidamenteTransacciones cortas con poca contención
    FOR UPDATE NOWAITFalla de inmediato con ORA-00054Pantallas de usuario que avisan «registro en uso»
    FOR UPDATE WAIT nEspera hasta n segundosReintento con tiempo límite
    FOR UPDATE SKIP LOCKEDOmite las filas bloqueadasColas de trabajo con varios procesadores

    Limitar el lote desde PL/SQL

    Si se limita el lote con ROWNUM dentro de la misma consulta con SKIP LOCKED, puede devolver menos filas de las esperadas, porque ROWNUM se evalúa antes de que se descarten las filas bloqueadas. Con un contador en el bucle, como en el código anterior, el reparto entre procesadores es más predecible.

    7.4 Interbloqueos y orden de bloqueo

    Un interbloqueo (ORA-00060) aparece cuando dos transacciones se esperan mutuamente. Oracle detecta el ciclo y aborta una sentencia, no la transacción completa, así que la sesión afectada queda con trabajo a medias y tiene que hacer ROLLBACK de forma explícita. Si se asume que Oracle «ya deshizo todo», se puede terminar haciendo COMMIT de una transacción incompleta.

    La forma de prevenirlo es una regla de diseño: bloquear siempre los recursos compartidos en el mismo orden, sin importar el sentido de la operación de negocio.

    7.5 Concurrencia optimista

    Cuando los conflictos son raros y hay muchos lectores, bloquear penaliza a todos para evitar un problema que casi no ocurre. La alternativa es una columna de versión: se lee la versión, se modifica con WHERE version = :leida y se incrementa. Si SQL%ROWCOUNT da 0, alguien más cambió la fila, así que se vuelve a leer y se reintenta. Lo que no se debe hacer es suponer que todo salió bien porque no hubo error: para el motor, un UPDATE que afecta cero filas es un resultado válido.

    EstrategiaCuándo usarlaCosto
    Pesimista (FOR UPDATE)El choque es poco frecuente pero costoso, por ejemplo una transferencia puntual de alto valorLas demás sesiones esperan
    Optimista (versión)El recurso se lee mucho y se escribe pocoLa aplicación debe reintentar
    SKIP LOCKEDReparto de trabajo entre varios procesadoresEl orden de procesamiento deja de ser estricto

    8. Disparadores (triggers) avanzados

    8.1 Puntos de disparo y orden de ejecución

    Un trigger de tabla puede ejecutarse en cuatro momentos respecto de una sentencia DML:

    1. BEFORE STATEMENT: una vez, antes de que la sentencia toque filas.
    2. BEFORE EACH ROW: por cada fila, antes de modificarla. Aquí se pueden asignar valores a :NEW.
    3. AFTER EACH ROW: por cada fila, después de modificarla.
    4. AFTER STATEMENT: una vez, cuando la sentencia termina.

    Si una tabla tiene varios triggers del mismo tipo, el orden entre ellos no está garantizado a menos que se use la cláusula FOLLOWS. Depender de un orden implícito es una causa típica de errores que aparecen y desaparecen.

    8.2 El error de tabla mutante

    Un trigger de fila no puede consultar ni modificar la tabla sobre la que se está ejecutando la sentencia. Oracle lo impide con ORA-04091 (tabla mutante), porque en ese momento la tabla está en un estado intermedio. La solución es el trigger compuesto (COMPOUND TRIGGER), que junta en una sola unidad los cuatro puntos de disparo y comparte variables entre ellos. Se recolectan los datos fila por fila y se procesan al final, en AFTER STATEMENT, cuando la tabla ya no está mutando.

    8.3 Triggers INSTEAD OF

    Una vista que combina varias tablas normalmente no admite DML. Un trigger INSTEAD OF intercepta la operación sobre la vista y la convierte en modificaciones sobre las tablas base. Así se puede dejar la vista como interfaz de escritura estable aunque el esquema interno cambie.

    8.4 Criterios de diseño

    ConvieneConviene evitar
    Usar triggers para reglas de integridad que no se pueden declarar como restricción (auditoría, valores derivados)Poner en un trigger mucha lógica de negocio, porque es invisible para quien lee el procedimiento y difícil de probar
    Mantener el trigger corto y delegar el trabajo en un procedimiento de un paqueteQue un trigger dispare otro que modifica la misma tabla, porque las cascadas son difíciles de seguir
    Asignar valores en BEFORE EACH ROW (:NEW.columna := ...)COMMIT dentro de un trigger. La transacción es de quien ejecutó el DML y solo se permite con una transacción autónoma
    Recolectar en AFTER EACH ROW y procesar en AFTER STATEMENTConsultar la propia tabla desde un trigger de fila
    Declarar el orden con FOLLOWS cuando importaSuponer un orden de ejecución entre triggers

    Un trigger de fila se ejecuta por cada fila, así que en una carga de un millón de filas sus costos se multiplican. Antes de una carga así hay que evaluar si el trigger se puede deshabilitar un momento (ALTER TRIGGER ... DISABLE) y reemplazarlo por una validación equivalente al final.

    9. Manejo de errores y diagnóstico

    9.1 Cómo funciona una excepción

    Cuando ocurre un error en el cuerpo de un bloque, el control salta a la sección EXCEPTION. Si no hay un manejador que coincida, la excepción pasa al bloque que contiene al actual y al final llega a quien llamó. Las excepciones pueden ser de tres tipos:

    • Predefinidas, como NO_DATA_FOUND, TOO_MANY_ROWS, DUP_VAL_ON_INDEX, ZERO_DIVIDE o VALUE_ERROR.
    • Errores de Oracle sin nombre, a los que se les asigna uno con PRAGMA EXCEPTION_INIT, como ORA-02291 (violación de llave foránea) o ORA-24381.
    • De aplicación, que se lanzan con RAISE_APPLICATION_ERROR(código, mensaje) usando códigos entre -20000 y -20999.

    9.2 WHEN OTHERS

    Un manejador WHEN OTHERS captura cualquier error. Tiene sentido en el nivel más externo de una operación, para registrar el error y relanzarlo, y en casi cualquier otro lugar es un defecto. Un WHEN OTHERS debería terminar siempre en RAISE o en RAISE_APPLICATION_ERROR. El compilador ayuda con esto: la advertencia PLW-06009 avisa cuando un manejador OTHERS no relanza la excepción, y desde 21c se puede silenciar de forma explícita con el pragma SUPPRESSES_WARNING_6009 en una rutina de reporte propia [8].

    9.3 Dónde ocurrió el error

    SQLERRM dice qué falló pero no dónde. Hay dos herramientas para eso:

    • DBMS_UTILITY.FORMAT_ERROR_BACKTRACE devuelve en texto la pila de llamadas, con la unidad y la línea donde se originó el error.
    • El paquete UTL_CALL_STACK (desde 12c) entrega esa misma información de forma estructurada: profundidad del error, número y mensaje de cada nivel, y unidad y línea de cada paso.

    Capturar los valores al inicio del manejador

    SQLCODE, SQLERRM y la traza corresponden a la excepción en curso. Si el manejador ejecuta antes otras sentencias que también producen errores, esos valores pueden cambiar. Lo más seguro es copiarlos a variables locales en la primera línea del manejador, o pasarlos como argumentos, como en el Código 9.1.

    9.4 Errores por fila en DML masivo: LOG ERRORS

    En las cargas masivas donde algunas filas pueden ser inválidas, el DML puede guardar cada fila rechazada en una tabla de errores y seguir con las demás, sin necesidad de PL/SQL. La tabla de errores se crea con DBMS_ERRLOG.CREATE_ERROR_LOG.

    Comparado con FORALL ... SAVE EXCEPTIONS, LOG ERRORS también funciona en sentencias SQL puras y deja los errores guardados en una tabla que se puede consultar. SAVE EXCEPTIONS es mejor cuando la reacción al error tiene que ejecutarse dentro del propio programa.

    10. Seguridad en PL/SQL

    10.1 Derechos del definidor y del invocador

    Por defecto, un subprograma se ejecuta con los privilegios de su dueño (derechos del definidor). Esto sirve como herramienta de seguridad: se puede dar EXECUTE sobre un paquete sin dar acceso directo a las tablas que maneja, y la aplicación solo puede hacer lo que el paquete permite. Con AUTHID CURRENT_USER el subprograma usa los privilegios de quien lo llama (derechos del invocador), lo que va bien para utilidades genéricas que deben trabajar con los datos de cada usuario.

    Derechos del definidor (AUTHID DEFINER)Derechos del invocador (AUTHID CURRENT_USER)
    Privilegios usadosLos del dueño del códigoLos de quien lo llama
    RolesNo se aplican dentro de la unidadSe aplican los roles habilitados del invocador
    Resolución de nombresEn el esquema del dueñoEn el esquema del invocador
    Uso típicoAplicaciones: exponer operaciones y no tablasUtilidades genéricas sobre objetos del propio usuario
    Riesgo principalUn dueño con demasiados privilegios puede permitir una escalada si hay inyecciónLa resolución de nombres se puede manipular si no se califican los objetos

    En derechos del invocador, desde 12c una unidad solo puede usar los privilegios de quien la llama si este le concedió INHERIT PRIVILEGES a su dueño (por defecto, PUBLIC lo tiene concedido). Revocarlo para dueños no confiables reduce el riesgo de que código ajeno aproveche los privilegios de quien lo llama.

    10.2 Capas de defensa

    1. Mínimo privilegio: cada cuenta recibe solo EXECUTE sobre los paquetes que necesita.
    2. Nada de SQL dinámico concatenado: variables de enlace y DBMS_ASSERT (sección 5).
    3. Restringir quién llama con ACCESSIBLE BY (sección 2.3) en los subprogramas internos.
    4. Calificar los nombres de objeto (esquema.objeto) en el código con derechos del invocador.
    5. Usar wrap solo si se distribuye código. Oculta el texto fuente, pero no es un cifrado fuerte ni reemplaza a los privilegios.
    6. No dejar secretos en el código. Contraseñas, claves y tokens van fuera del texto PL/SQL. La documentación de Oracle tiene una sección sobre cómo proteger información sensible en PL/SQL.

    11. Rendimiento, instrumentación y diagnóstico

    Antes de optimizar hay que medir. Una mejora sobre la parte equivocada no reduce el tiempo total. Oracle tiene herramientas distintas según lo que se quiera averiguar.

    11.1 Qué herramienta usar para cada pregunta

    PreguntaHerramienta
    ¿Dónde se va el tiempo? ¿Es PL/SQL o SQL?Perfilador jerárquico DBMS_HPROF [6] [7]
    ¿En qué orden se ejecutaron los subprogramas?API de traza DBMS_TRACE [7]
    ¿Dónde se declara y se usa cada identificador? ¿Hay variables sin usar?PL/Scope (PLSCOPE_SETTINGS)
    ¿Qué cubren las pruebas?DBMS_PLSQL_CODE_COVERAGE

    11.2 El perfilador jerárquico

    El perfilador jerárquico informa dónde gasta el tiempo un programa PL/SQL, organizado por las llamadas entre subprogramas. A diferencia de un perfilador plano, muestra quién llama a quién, cuántas veces y cuánto tarda cada ruta, incluyendo a los descendientes. Registra por separado el tiempo de SQL y el de PL/SQL, y no hace falta preparar ni recompilar el código [6].

    Tiene dos componentes [6]:

    • La recolección de datos, integrada en la máquina virtual de PL/SQL y controlada con START_PROFILING y STOP_PROFILING.
    • El analizador (DBMS_HPROF.ANALYZE), que procesa el archivo en bruto y llena las tablas de análisis.

    Las métricas, en microsegundos [6]:

    MétricaColumnaSignificado
    LlamadasCALLSCuántas veces se llamó al subprograma
    Tiempo de funciónFUNCTION_ELAPSED_TIMETiempo en el propio subprograma, sin descendientes
    Tiempo de subárbolSUBTREE_ELAPSED_TIMETiempo del subprograma más el de sus descendientes
    Tiempo de descendientes(derivado)Subárbol menos función

    Las tablas que crea el analizador son DBMSHP_RUNS (una fila por análisis), DBMSHP_FUNCTION_INFO (una por subprograma y corrida) y DBMSHP_PARENT_CHILD_INFO (una por cada pareja llamador y llamado) [6]. También se puede generar un informe HTML directamente desde la línea de comandos con la utilidad plshprof.

    11.3 PL/Scope y trazas

    PL/Scope no mide tiempo. Es una facilidad del compilador que registra los identificadores y las sentencias del código y los expone en vistas como ALL_IDENTIFIERS y ALL_STATEMENTS. Sirve para análisis estático: saber dónde se usa una variable, qué impacto tendría renombrarla o qué código nunca se referencia.

    La API de traza DBMS_TRACE registra el orden en que se ejecutan los subprogramas que se indiquen, con el nivel de detalle que se elija, en tablas que se pueden consultar [7]. Responde a «¿qué se ejecutó y en qué orden?», no a «¿qué fue lento?».

    11.4 Instrumentación mínima para producción

    Un programa que no dice qué está haciendo es muy difícil de diagnosticar cuando falla en producción. DBMS_APPLICATION_INFO deja el módulo y la acción visibles en V$SESSION y en las trazas SQL.

    11.5 Advertencias del compilador y compilación condicional

    Con PLSQL_WARNINGS el compilador avisa de problemas antes de ejecutar el código: variables sin usar, código inalcanzable, conversiones implícitas costosas, manejadores OTHERS que no relanzan. La compilación condicional permite incluir código de diagnóstico solo cuando una bandera lo pide, sin costo en producción.

    Con PLSQL_OPTIMIZE_LEVEL = 2 (el valor predeterminado) el compilador reordena y simplifica el código. Con 3 activa además la expansión agresiva de subprogramas en línea (inlining), que también se puede pedir a mano con PRAGMA INLINE(subprograma, 'YES'). Si se necesita depurar con un depurador, se compila con nivel 1 [2].

    12. Calidad de código y pruebas

    12.1 Pruebas unitarias con utPLSQL

    El código que vive en la base de datos también necesita pruebas automáticas. utPLSQL es un framework de pruebas unitarias de código abierto para PL/SQL. Las pruebas son paquetes con anotaciones en comentarios que el framework encuentra y ejecuta.

    12.2 Lista de revisión de código

    ÁreaPregunta de revisión
    Rendimiento¿Hay SQL dentro de un bucle que podría ser una sola sentencia o un FORALL?
    Memoria¿Todo BULK COLLECT tiene LIMIT o un tamaño acotado por naturaleza?
    Seguridad¿Hay SQL dinámico? ¿Los valores van enlazados y los identificadores validados?
    Errores¿Algún WHEN OTHERS termina sin RAISE?
    Concurrencia¿Se lee un valor y luego se escribe sin bloquear ni usar versión?
    Bloqueos¿Se toman varios bloqueos siempre en el mismo orden?
    Transacciones¿Quién decide el COMMIT? ¿Algún subprograma reutilizable confirma por su cuenta?
    Triggers¿Tienen lógica que debería estar en un paquete? ¿Consultan su propia tabla en un trigger de fila?
    Nombres¿Se respetan los prefijos y el nombre dice qué hace el elemento?
    Pruebas¿Hay una prueba para el caso normal y una para cada excepción de negocio?

    12.3 Control de versiones y despliegue

    El código PL/SQL se versiona como cualquier otro: un archivo por unidad en un repositorio, escrito con CREATE OR REPLACE para que el script de despliegue se pueda repetir sin problema. Los cambios de estructura (tablas) se manejan como migraciones numeradas, separadas del código de las unidades. Después de cada despliegue se revisa que no queden objetos inválidos (Código 1.2).

    15. Conclusiones y buenas prácticas

    Lo difícil de PL/SQL no es escribir código que funcione, sino que siga funcionando cuando crece el volumen, cuando llegan sesiones concurrentes, cuando el esquema cambia y cuando alguien intenta abusar del sistema. De todo lo revisado, me quedo con cuatro ideas:

    1. Cruzar la frontera entre los dos motores tiene un costo, y cada técnica de rendimiento busca cruzarla menos veces (SQL puro, lotes, funciones en tubería, macros).
    2. El motor solo protege lo que se le pide proteger. La consistencia ante concurrencia se diseña con bloqueos, versiones y un orden fijo.
    3. Un error silenciado es peor que uno visible. Hay que registrarlo, relanzarlo y dejar la traza de dónde ocurrió.
    4. Lo que no se mide ni se prueba no se puede garantizar, así que conviene perfilar antes de optimizar y automatizar las pruebas.

    Lista de buenas prácticas

    1. Si la lógica cabe en una sola sentencia SQL, escribir esa sentencia.
    2. Usar LIMIT en todo BULK COLLECT y evaluar COUNT = 0 en lugar de %NOTFOUND justo después del FETCH.
    3. Enlazar siempre los valores y validar los identificadores con DBMS_ASSERT.
    4. Agrupar la lógica en paquetes, con la especificación más pequeña posible.
    5. Hacer que un WHEN OTHERS registre y relance, nunca que silencie.
    6. Bloquear los recursos compartidos siempre en el mismo orden.
    7. Preferir SKIP LOCKED para repartir trabajo y el control de versión donde los conflictos son raros.
    8. Dejar las transacciones autónomas para el registro y la auditoría.
    9. Mantener los triggers cortos y usar COMPOUND TRIGGER si se necesita consultar la propia tabla.
    10. Dar a las cuentas de aplicación solo EXECUTE sobre los paquetes.
    11. Medir con DBMS_HPROF antes de optimizar y marcar módulo y acción con DBMS_APPLICATION_INFO.
    12. Compilar con las advertencias activadas y revisar USER_ERRORS y los objetos inválidos después de cada despliegue.
    13. Escribir pruebas para el caso normal y para cada excepción de negocio.
